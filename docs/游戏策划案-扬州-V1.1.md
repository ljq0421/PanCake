# 一、章节核心目标

扬州章节建议安排在中国篇中后段，共 **12天**。

章节核心不是继续提高点击速度，而是把玩家从：

**“快速制作一份早餐”**

推进到：

**“提前备货并同时完成多桌早茶套餐”。**

核心三系统：

| 定位 | 内容 | 核心行为 |
|---|---|---|
| 主玩法 | 烫干丝 | 切丝、三烫、调味 |
| 辅玩法 | 三丁包 / 翡翠烧卖 | 批量装笼、蒸制、备货 |
| 快速商品 | 绿杨春茶 | 快速拿取、套餐补全 |

扬州最终体验关键词：

**备料、调度、组合、从容。**

# 二、与前面城市的难度差异

天津主要压力：

**顾客多、单较短。**

武汉主要压力：

**连续制作、即时操作。**

扬州：

**顾客数量减少，但是每个订单包含更多商品。**

因此扬州最终日不需要26～30名顾客。

控制在：

**20组顾客。**

但是每组平均约：

**2.5～3.5个商品单位。**

最终形成：

> 人看起来没有天津那么多，但工作台一直有事情做。

# 六、核心主玩法：干丝备料

干丝不能每来一名顾客就从整块豆干开始切。

正确结构：

```text
整块豆干
↓
切丝备料
↓
产生多份干丝库存
↓
顾客点单
↓
取1份
↓
三烫
↓
调味
↓
出餐
```

因此玩家真正需要判断的是：

> **什么时候应该提前补一批干丝。**

# 十、三烫操作

每一份干丝从备料盘拖入漏勺。

玩家进行：

```text
下锅
↑
提起

下锅
↑
提起

下锅
↑
提起
```

每次有效浸入约：

**0.25～0.35秒。**

完整三烫：

约：

**1.1～1.4秒。**

完成三烫后：

扬州核心是：

**切 + 烫**

**点五个调料盒。**

# 二十四、切换顾客时托盘内容保留

这是非常重要的技术/交互规则。

例如：

顾客A：

```text
干丝 ✓
茶 ✓
烧卖 □
```

此时烧卖还没熟。

玩家可以点击顾客B：

先完成B订单。

之后重新点击A：

之前已经放入的商品：

**仍然存在。**

因此每个OrderData需要拥有：

```text
StagedItems
```

而不是工作台只有一个真正的公共托盘状态。

视觉上只是：

> 点击哪个顾客，就显示哪个订单的暂存内容。

这会让复杂套餐调度非常顺滑。

# 六十、扬州章节最终定义

扬州不是“早餐制作速度考试”。

它应该成为中国篇第一次真正的：

# 工作流调度考试

玩家从：

> 一份一份烫干丝

逐步学会：

> 提前切一批干丝。

再学会：

> 包子在蒸的时候继续服务顾客。

再学会：

> 两种蒸点要分别安排库存。

最后学会：

> 面对一桌缺烧卖、另一桌缺茶、第三桌结伴大单时，判断当前最值得做的事情。

最终玩家获得的不是：

> “我的手速变快了。”

而是：

> **“我已经知道怎么经营一家早茶铺了。”**

这就是扬州和天津、武汉、西安、广州最重要的玩法差异。
:::

其中我认为有两个设计值得现在就固定下来：**扬州新增“每个订单独立暂存的早茶托盘”**，以及**每个城市使用独立营业资金**。前者会直接决定复杂套餐是否好操作；后者则会决定做到中国第6～8城以后，城市设备成长还是否有意义。
