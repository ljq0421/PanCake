# 历史归档：五区同屏实体经营与顾客托盘交付

> 已退休：本文件只保留演进记录，不可作为当前实现依据。请使用 `docs/four_area_workstation_runtime.md`。

## 历史运行时合同

当时的营业场景 `four_area_workstation.tscn` 曾拥有现磨豆浆、油条、煎饼、成品饮品和蒸笼五个站点。生产操作不会打开覆盖页、关闭按钮或切换页面；日结、成长购买与设置覆盖层不受影响。订单变化只更新顾客、只读点单卡和共享递餐托盘，不改变站点焦点，也不暂停其他设备。

共享递餐托盘固定三格，格序与正式订单 `items` 下标一一对应。每格同时显示请求剪影和实际餐品；同项数量大于一时叠放在同格并显示 `已放/需求`。错商品和错温度允许入格并进入正式结算，结构性错误（非活动订单、非法来源、来源未完成、格已满）才拒绝。未装齐的整盘递交会回弹并列出每个缺少项。

所有拖拽沿用约 10px 启动阈值。无效释放不会调用业务事务，因此不扣库存；事务失败会恢复来源、生产设备、订单与库存快照。结算后顾客生成可见付款，玩家点击收币后才记入金币并继续下一单。

## 共享事务接口

`ProductSourceRef` 的持久来源合同为：

```gdscript
{
    "source_kind": &"inventory|heater_slot|youtiao_output|soy_output|steamer_layer|pancake_ready|pancake_holding",
    "source_index": -1,
    "product_id": &"",
}
```

- `GameSessionStore.stage_product_to_order(source_ref, order_id, item_index)`：预览来源、原子取出、生成或收取唯一产品实例，并附加到指定订单格；返回 `will_match` 与 `mismatch_reasons`。
- `GameSessionStore.remove_staged_product(order_id, item_index, disposition)`：只允许未加工常温包装饮品走 `return_stock`；热饮和其他加工品只能走可见 `waste`。
- `GameSessionStore.handoff_order_tray(order_id)`：仅当三格中所有需求数量完整时调用正式结算，随后创建待点击付款。

订单中的 `attached_products` 是托盘内容的唯一权威数据，不建立第二份托盘库存。产品实例记录 `reservation_origin` 和 `return_policy`；历史存档中缺少来源字段的实例按 `waste_only` 恢复，避免猜测可退来源。

## 实体站点

- 成品饮品柜由空柜壳、四条动态货道、四个按住补货位和实体加热位组成。库存为零时货道真正空置；每 0.5 秒完成一份补货才扣费并上架，松开保留未完成进度。
- 油条站由面胚拖入炸篮，通过设备按钮启动与升篮，再从沥油输出位拖出。
- 现磨豆浆站由豆料拖入料口，分别操作加水和启动部件，再从机器或杯架拖出。
- 蒸笼由半成品拖入指定层，逐层启动，熟成后从对应层拖出。
- 煎饼制作手势不变；现做成品和暂存成品都改为实体拖入顾客托盘。

锁定站点仍保留设备轮廓和浅色搪瓷/黄铜锁盖。点击锁盖只把所有缺失条件写入现有状态栏，不创建生产面板。

- 自动事务检查覆盖错品、错温、数量堆叠、退库存、加工品废弃、满格、重复交付、快照回滚和存档恢复。

- D3D12 GPU 真实指针检查覆盖无效释放、货道到托盘、托盘退柜、未装齐回弹、货道到加热位、热饮到托盘、整盘递交和点击收币，并在 `1920x1080` 与 `1280x720` 截图。
