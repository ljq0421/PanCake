# 天津、武汉全解锁营业素材锯齿排查

日期：2026-09-12。范围为两城全商品、最高等级设备的营业界面，以及制作、库存、订单和交付相关画面。本次只排查，新增文档与截图证据，没有修改生产代码、图片或导入设置。

## 结论

两章都有与武汉双勺相同的缩小采样问题。最明显的不是整张背景，而是独立叠加的小食物、工具、密集网格和订单缩略图。不能仅凭“原图大”或“没有 mipmap”判定严重度；以下已确认项同时核对了运行截图、实际使用的素材和渲染设置。

| 范围 | 已在实际截图确认的表现 | 程度及建议顺序 |
|---|---|---|
| 天津薄脆、香葱碎 | 斜边、细轮廓与密集内纹呈小台阶、碎点 | 优先 |
| 天津成品豆浆杯 | 杯口圆弧、杯侧棕线有像素阶梯 | 优先 |
| 天津熟油条（库存与锅内） | 斜向外沿和内部金黄曲线细碎，锅内小尺寸更突出 | 优先 |
| 天津炸篮 | 密网与倾斜边线粗细不均、出现阶梯 | 优先，但修复时需兼顾细网清晰度 |
| 武汉订单热干面、葱花 | 面碗绿色环线断成点划状，面条、葱花密集细节呈噪点 | 优先；武汉订单比天津更小 |
| 武汉面篮、篮内面条 | 柄端斜边、篮口弧线和面条细线有台阶与碎点 | 优先 |
| 武汉拌面筷子 | 操作时长斜线边缘较硬、细线不均 | 中等 |
| 武汉摊蛋液铲、切块铲刀 | 金属头轮廓和木柄斜线可见台阶；旁边已修复的蛋液勺更平滑 | 中等 |
| 天津订单商品小图 | 煎饼、油条、豆浆及配料轮廓有硬边，720p更明显 | 中等 |
| 两城顾客；天津鸡蛋、火腿、装袋煎饼；武汉碗内大尺寸食物层 | 细发丝、衣扣或部分细纹略粗糙，主轮廓整体连续 | 较轻，不与最明显项等同 |

720p下多数小图问题更容易看见。截图是固定操作时刻的帧，因此以上确认的是可见的空间锯齿与碎点，不把未测量的动画闪烁当成已验证结论。

## 原因与实际素材

### 天津

下列源图位于 `resource/art/TianJin/`，均为1254×1254，导入未生成mipmap。天津相关节点继承默认纹理过滤，没有显式开启线性mipmap采样。`FoodInk` 棕色描边处理也不能替代缩小预过滤。

| 文件 | 去除透明留白后的采样区域 | 1080p实际显示约 | 缩小约 |
|---|---:|---:|---:|
| 鸡蛋.png | 528×628 | 51×61 | 10倍 |
| 薄脆.png | 948×622 | 90×59 | 10倍 |
| 香葱碎.png | 588×521 | 72×64 | 8倍 |
| 火腿片.png | 824×610 | 86×64 | 10倍 |
| 成品豆浆杯.png | 586×633 | 82×89 | 7倍 |
| 熟油条.png（库存） | 978×923 | 100×94 | 10倍 |

720p显示尺寸再乘2/3。食材尺寸入口为 `TianjinWorkbenchLayout`、`WorkstationSlotView.BuildStackedStock`，实际接入为 `PancakeWorkbenchPresentation`。

炸篮为 `resource/art/TianJin/Workbench/阶段工作台-升降滤篮-v3.png`（1471×607），显示约291×134；锅内油条限框约89×62。入口为 `FryerVisualView`。其导入同样未生成mipmap。

### 武汉

`WuhanWorkstationView` 已设置 `LinearWithMipmaps`，但下列1254×1254独立纹理仍未生成mipmap，所以只修改父节点并没有解决它们的缩小问题：

- `通用热干面漏勺_v2.png`：面篮限框156×177；`漏勺中的熟面状态.png` 被进一步放入篮内的小区域。
- `拌面筷子_v2.png`：操作时限框148.5×148.5，并旋转。
- `豆皮手动翻面铲.png`、`豆皮切块铲刀.png`：主要动作限框138×91；静置或其他手势状态还会更小。
- `碗中熟面基础层.png`、`拌匀热干面基础层.png` 及葱花、辣油、牛肉覆盖层：大碗内限框约246×125，部分配料更小。大碗表现较轻，不把所有覆盖层都列为严重。

定位入口为 `WuhanWorkstationView.DrawCooker/DrawLoadedBasket/DrawMixStation/DrawIngredientMotion`、`WuhanDoupiPresentation.DrawPanMotion/DrawEggMotion` 和 `WuhanWorkstationGestures.DrawGesture`。

### 订单及预览不能只靠工作台父节点修复

`OrderBubbleView` 的主餐限框62×46、配料44×40、副餐46×36。武汉还有0.86×0.88的层级缩放，1080p主餐实际限框约47×35，720p约31×23。热干面订单使用 `热干面空碗_v2.png` 与 `拌匀热干面基础层.png` 合成，实际使用区域大约千像素宽；葱花使用 `葱花覆盖层.png`。这些纹理没有mipmap，订单节点也没有线性mipmap过滤。

天津订单使用 `装袋后的通用煎饼果子.png`、`熟油条.png`、`成品豆浆杯.png`、`香葱碎.png`、`薄脆.png`、`火腿片.png` 等真实资源，存在相同配置缺口。

## 已修复、正在更新及不同原因的项目

- 武汉面糊勺和蛋液勺：两张v2素材已有mipmap，工作台使用线性mipmap过滤，本轮画面平滑，保持通过。
- **排查期间工作区里的豆皮成品已经更新**：`DoupiPieces_v1/piece-01.png`～`piece-04.png` 已启用mipmap，库存由工作台过滤，`CreateDoupiPiecePreview` 也已显式设置 `LinearWithMipmaps`。它们不再列入当前待处理风险。
- 订单豆皮也已切换为 `DoupiPieces_v1/piece-01.png`。不能再按旧的 `单块三鲜豆皮成品.png` 追踪修复；新图虽有mipmap，订单所在节点仍缺少相应过滤，应随订单整体复核。旧成品分片画面的评价不作为新版本的问题证据。
- 两城大背景为1672×941级别，1080p约放大1.15倍，720p约缩小1.31倍，当前主轮廓较平滑，不是小图十几倍缩小的同级问题。天津静置的面糊勺和酱刷已画入背景，不应误报为独立叠图。
- 天津制作中的煎饼外沿部分由 `PancakeCanvas.DrawEllipse` 调用未传抗锯齿参数的 `DrawCircle` 绘制。此类几何边缘应单独处理，不能承诺只加mipmap全部修复。

## 同类配置风险，但未确认动态严重度

- 两城飞币实际走 `CashPendantFeedback`，1254×1254的 `金币图标.png` 从38×38继续缩到约25×25，最后约6×6淡出。纹理及节点仍有过滤缺口，本轮未专门捕获飞币的连续帧，不宣称已经验证闪烁程度。
- 天津拖拽商品、武汉热干面交付预览由 `DragService` 重挂到overlay，不自动继承工作台过滤。武汉豆皮预览已有单独修正，需区分。
- 天津舀面糊、刷酱、刮板等短暂独立工具状态有相同配置风险，本轮未逐帧捕获全部这些手势。

## 验证范围及后续建议

天津使用现有 `VisualCapture.tscn`：第15天、设备Lv3，1080p/720p满库存与装袋状态，另检查1080p制作/升篮状态。武汉使用 `WuhanVisualCapture.tscn` 的 `--layout`、`--animations`，检查1080p/720p，包含Lv3完整商品、满库存、拌面、倒蛋、切块与交付。武汉夹具以第8天运行；已核对第8天和第12天的可用配方、商品集合相同，最高等级设备由夹具显式配置，因此覆盖全商品工作台。未穷举全部顾客外观、每个动画时刻、手账及结算页面。

建议优先处理上述确认项，同时配置实际纹理mipmap和它所在CanvasItem的线性mipmap过滤；随后在两种分辨率、静置和移动状态对比检查，保留棕色轮廓与网格清晰度。订单、飞币和重挂父节点的交付预览需要各自覆盖。无需重新生成所有图片，也不建议机械地对整个素材目录宣称“全部修复”。
