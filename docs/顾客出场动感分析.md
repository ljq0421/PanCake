以下保留原动感分析与后续建议；涉及未勾选功能的段落不表示已实现。

**可以，而且我建议把“顾客登场”作为下一批优先打磨的动效。**结合你现在“顾客半身靠近柜台、订单卡靠近头顶”的布局，最适合的不是顾客突然放大弹出，而是：

> **有人走近柜台 → 停下时身体轻轻回弹 → 订单卡出现 → 自然等待。**

**顾客可以有一点果冻感，但应该比食物更克制。**食物强调柔软，顾客强调步伐、身体惯性和性格。

## 一、最推荐的登场方案：短距离走近，而不是从桌下蹦出来

我建议第一版采用：

### **“短距离斜向就位 + 停步轻回弹 + 订单卡错峰出现”**

不必让每位顾客从屏幕最左边一直走到自己的位置。尤其是中间已经有顾客时，长距离横穿会与现有人物、订单卡产生遮挡。

可以只表现“走到柜台前的最后一步”：

顾客在最终站位的侧后方出现，向柜台靠近一点，身体伴随很小的步伐晃动，然后站稳。

下面是按 **1920×1080** 设计分辨率给出的首轮调参建议，需要结合实际人物尺寸验证。

| 阶段   |        建议时间 | 画面表现                     |
| ---- | ----------: | ------------------------ |
| 走近   | 0.00～0.28 秒 | 从站位侧后方移动到位，速度逐渐放缓；身体轻晃一次 |
| 订单出现 | 0.24～0.36 秒 | 与人物停步重叠，订单底板轻轻展开，内容快速显示  |
| 停步回弹 | 0.28～0.44 秒 | 身体轻微压缩、恢复，只回弹一次          |
| 进入等待 |   约 0.44 秒后 | 人物安静站定，只保留很弱的待机动作        |

**整套表现约半秒，但不是“让玩家等半秒才能操作”。**订单一旦清楚可读、交付目标已经稳定，就可以进入可服务状态，不用等身体最后那一点回弹结束。

### 人物移动建议有多大？

第一版可以从这些值开始：

```text
横向移动：24～48 px
纵向移动：8～16 px，方向根据场景通道确定
靠近时整体缩放：0.97 → 1.00
步伐上下起伏：2～3 px
身体左右倾斜：不超过 ±1°
```

这里的 `0.97 → 1.00` 只是稍微表现“靠近”，**不是从很小的人物放大到正常尺寸**。

入场方向应与场景空间一致。有明确的门口、街道或通道，就沿那个方向；没有可见通道时，先做站位附近的短距离就位，不必强行设计一条穿过其他顾客的路线。

## 二、顾客的“果冻感”放在停下的一瞬间

我不建议顾客一路弹跳，更不建议像食物一样明显压扁。

**最适合加入轻形变的时刻，是走到位置、收住脚步的时候。**

例如：

```text
正常尺寸
(1.000, 1.000)

轻微下压
(1.025, 0.976)

小幅恢复
(0.990, 1.010)

回到正常
(1.000, 1.000)
```

整个回弹控制在 **0.14～0.20 秒**左右即可。

它要表达的是：

> **“走过来，站住了。”**

而不是：

> “这个人是一块果冻。”

支点建议放在人物下半身被柜台遮住的位置附近，让上半身产生很轻的惯性。脸部明显被拉长、眼睛被挤扁，就说明幅度过大了。

**即使现在只有一张完整顾客 PNG，也能先实现整体移动、缩放和倾斜。**Godot 的 `Node2D` 本身就提供这些变换属性，不需要为了第一版登场效果先制作骨骼动画。([Godot Engine documentation][1])

不过，整张图片的移动只能模拟身体起伏；**真正的独立点头、眨眼、挥手，需要拆分部件或增加对应帧**，不能把整体图片摇晃当成已经实现了这些动作。

## 三、订单卡要有登场感，但不要跟着人晃

这部分很重要，因为顾客是氛围主体，**订单才是玩家正在读取的操作信息**。

我建议：

**人物先出现，订单卡稍晚一点出现，但两者的动画重叠进行。**

订单卡不必从零缩放出来，可以让底板从约 `0.96` 恢复到 `1.00`，再配很短的淡入。菜品和配料内容快速显示后就保持稳定。

对你现在统一宽度、支持多种食物的订单卡，尤其建议：

**一张订单里的全部需求同时呈现，不要煎饼先出来、豆浆隔一会儿出来、油条再出来。**否则玩家可能在信息还没显示完整时就开始判断订单。

另外：

**人物呼吸、点头、接餐时，订单卡不要同步上下漂动。**

卡片可以固定在对应站位上方，位置按人物身高适当调整，但不继承人物的身体回弹。这样既能靠近头顶，也不会让玩家追着晃动的小图标阅读。

Godot 的 Tween 支持并行动画与后续串联，因此“人物移动、身体收尾、订单出现”可以交叠安排，不需要一段播完才能开始下一段。([Godot Engine documentation][2])

## 四、出现之后，再补一点“这个顾客活着”的感觉

只做登场、随后完全静止，也可以作为第一版。但我建议后续补上少量等待和离开动作，形成一个完整循环。

| 场景     | 建议表现               | 要避免的情况         |
| ------ | ------------------ | -------------- |
| 正常等待   | 很轻的身体起伏，偶尔改变一次姿势   | 所有顾客持续左右摇摆     |
| 收到一件食物 | 小幅身体回应，对应订单项更新     | 多食物订单每交一件就全身庆祝 |
| 整单完成   | 满意表情、轻微点头或身体前倾     | 大幅跳跃，挡住旁边订单    |
| 等待过久   | 在耐心状态变化时，做一次轻微不满动作 | 不断抖动、闪红、发出催促声  |
| 离开     | 沿合理方向短距离退场，订单卡先收起  | 突然消失，或向下掉进桌子里  |

### 待机动作应该很弱

第一版可以只做 **1～2 px 的轻微起伏**，周期约 **3～5 秒**，并让每位顾客的起始相位错开。

不是所有人都必须一直动。我的建议是：**大部分时间安静站着，偶尔出现小动作。**

等以后拆出眼睛、头部，再增加眨眼和点头。眨眼、抿嘴、看向食物这类局部动作，可以作为第二轮投入，不必第一版就全部补齐。

### 顾客之间可以有动作差别，但先不改变玩法

后续可以做“稳重、轻快、活泼”几种视觉参数：有的人身体晃动小，有的人停步稍轻快，有的人完成后回应更明显。

但建议先保持**相同的订单可用时点**，差异主要放在姿态和收尾动作上。不要因为某个顾客动画比较慢，就无意中改变他的有效等待时间、服务难度或到店节奏。

## 五、Godot 实现时，重点把这三个部分分开

建议沿用上一轮“逻辑层稳定，视觉层运动”的原则：

```text
CustomerSlot                 固定站位、顾客状态
├── DeliveryArea             稳定的交付判定区
├── BodyMotion               入场、退场位移
│   └── BodyReaction         停步回弹、轻微身体反应
│       └── CustomerSprite   顾客图片
└── OrderAnchor              固定在站位上方
    └── OrderCard            订单卡
```

这是建议结构，不要求你的现有场景必须完全按这些名字重建。

### 1. 人物动画不要带着交付区域一起晃

玩家把早餐拖给顾客时，目标应该稳定。订单卡与交付判定区不要挂在负责身体形变的节点下面。

同样，入场和待机不能同时抢着修改同一个节点的同一个属性。可以分层处理，或者等入场结束再启动待机；Godot 官方也明确提醒，应避免多个 Tween 同时修改同一对象的同一属性。([Godot Engine documentation][2])

### 2. 顾客必须一直在柜台后面

建议的视觉前后关系是：

```text
场景背景 → 顾客 → 柜台前景及桌面设备 → 订单信息
```

Godot 的 `ZIndex` 可以控制同一画布层内的绘制前后关系，但它**不会同步改变输入事件的处理顺序**，所以遮挡与交付判定需要分别检查。([Godot Engine documentation][3])

尤其要注意：**如果柜台已经画死在一整张背景图里，仅调整人物的 ZIndex，不能让背景中的柜台局部自动挡住人物。**这种情况下，需要单独的柜台前景遮挡图，或限制人物的可见区域，避免入场时身体露到桌面上。

### 3. 耐心计时不能被入场动画偷偷吃掉

我建议明确一个业务状态：

**订单完整可读 + 顾客已就位 + 可以交付 → 开始服务与耐心计时。**

这个状态由顾客逻辑决定，不依赖装饰 Tween 的 `Finished` 才能触发。减少动效、跳过动画或中途关闭场景，都不应该让顾客卡住。

若现有配置规定某个时刻开始接待，就把短入场表现安排在那个时刻之前，而不是在原有时间后面再追加一次等待。

创建动画时可以使用顾客节点的 `CreateTween()`，它会把 Tween 绑定到该节点；对象池回收时仍建议主动停止动画并恢复位置、缩放与透明度，防止下次复用时残留上一位顾客的状态。([Godot Engine documentation][4])

## 我建议你第一版就做这一套

**短距离走近 → 停步轻回弹 → 订单卡快速出现 → 安静等待 → 完成后轻回应、短距离离开。**

先用现有顾客 PNG，不急着增加全身走路、复杂骨骼、挥手或大量表情。声音也先保持克制：订单就绪时一个很轻的提示即可，不必每位顾客都响一次门铃、喊一次欢迎语。

**核心是让玩家感到“又有一位客人来到我的早餐铺”，而不是“界面又刷出了一张顾客图片”。**
