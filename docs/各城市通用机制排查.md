# 各城市通用机制排查

日期：2026-09-09。范围：天津、武汉、西安、广州、扬州的玩法入口、营业控制、顾客与订单、库存、交互、评分、存档与经营首页，以及相关配置和测试入口。

本次是静态代码排查，未修改游戏逻辑，也未执行新的运行测试。下文区分已确认规则、可共享实现和需要确认的玩法调整；建议不等于已批准的新规则。

## 可以继续统一的机制

### 1. 顾客位置与交付目标（高优先级）

- 现状：天津使用 `CustomerQueue.CustomerAtSlot`；武汉使用 `slots[i]`，西安、广州使用列表序号取顾客；扬州也按等待列表显示。
- 影响：列表删除前方顾客后，后方顾客会换显示位置。拖拽期间的目标稳定性也需要统一验证。
- 建议：共享“入场分配位置、离场释放位置、按顾客ID确认交付”的机制，订单气泡、耐心条和收餐区域绑定同一个顾客。顾客进出动画与城市美术可不同。
- 定位：`Scripts/Customers/CustomerQueue.cs`、`CustomerRuntime.cs`；各城市 `DayScreen` 的顾客渲染与交付回调。

### 2. 交付确认、扣库存与取消（高优先级）

- 现状：前四城已有 `OrderProgress` 和 `DayController.TryDeliverItem`，但城市入口及拖拽实现不同；扬州由 `YangzhouOrder.Stage/Serve` 管理。
- 建议：统一校验顾客仍有效、商品仍需要、库存仍可用；成功后提交一次订单进度、耐心恢复和结算事件；重复操作不得重复扣货或计款。动画取消后，不应留下未交付却已扣库存的状态。
- 可以共享交付结果和提交时机；武汉豆皮批量出餐、扬州整盘出餐应保留独立策略。批量交付数量和错配处理不要未经确认统一。
- 定位：`Scripts/Core/DayController.cs`、`Scripts/Orders/OrderProgress.cs`、`Scripts/Interaction/DragService.cs`、`Scripts/Yangzhou/YangzhouOrders.cs`。

### 3. 暂停、失焦、弹窗与切换页面（高优先级）

- 现状：各 `DayScreen` 分别维护手动暂停、失焦、弹窗、页面可见性和结束状态。天津区分手动暂停与失焦暂停；扬州失焦调用 `Session.Pause(true)`，恢复策略另行实现。
- 建议：共用交互许可与暂停原因管理，统一冻结顾客、烹饪、补货计时；弹窗关闭或焦点恢复不能误解除其他暂停原因。共享取消拖拽、长按、划动和临时动画的入口。
- 定位：各城市 `DayScreen` 的 `CanInteract/CanWork`、`_Process`、`_Notification`；`DragService`、`StockGesture`、`XianSurface`、`YangzhouSurface`。

### 4. 结算保存与失败重试（高优先级）

- 现状：`SaveService` 已有保存失败回滚；西安、广州和扬州界面提供重试。天津 `OnDayFinished`、武汉 `OnFinished` 在 `CommitDay` 成功前设置 `_committed = true`，失败分支没有对应的重试流程。
- 建议：共用“保留待保存成绩→尝试保存→成功后标记提交→允许离开”的流程；失败保留成绩并可重试，重复点击不重复奖励。
- 金币收益按历史最高收入的增量发放，`CommitDay` 和 `CommitYangzhou` 已采用相同原则，可合并这部分提交逻辑。
- 定位：`Scripts/Core/SaveService.cs`、`YangzhouSave.cs`；各城市 `DayScreen` 的结算方法。

### 5. 库存容量、补货计时与成品先入先出（中优先级）

- 现状：`RefillableStock`、`GuangzhouStock`、`EggRiceWineRuntime`、`SoyMilkTrayRuntime` 等重复实现库存与补货状态；武汉原料补货计时还由界面字典维护。馍、豆皮、蒸点等分别保存成品质量队列。
- 建议：共享容量、剩余量、补货状态、完成事件、数量校验和带质量信息的先入先出库存。容量、耗时、每次消耗量由商品或设备配置提供；取杯、盛汤、蒸制等制作过程保留。
- 补货期间能否使用剩余库存、点击还是长按补货，是需确认的交互规则，不应仅因抽取公共类而改变。
- 定位：`Scripts/Inventory`、`Scripts/Wuhan/WuhanInventory.cs`、`Scripts/Xian/XianInventory.cs`、`Scripts/Guangzhou/GuangzhouInventory.cs`、`Scripts/Yangzhou/YangzhouProduction.cs`。

### 6. 营业阶段与统一时钟（中优先级）

- 现状：前四城复用 `DayController`，扬州另有 `YangzhouSession`。公共开门倒计时3秒，扬州有5秒可操作备货；一般收尾均为15秒，扬州首日教学允许不限时收尾。扬州还使用小时间步处理跨阶段更新。
- 建议：共享阶段切换、时间推进、停止接客、收尾和结算事件，将准备时长、是否可备货、教学收尾保护做成配置或策略。对低帧率、一次跨越阶段的大时间步统一验证。
- 定位：`Scripts/Core/DayController.cs`、`Scripts/Yangzhou/YangzhouSession.cs`。

### 7. 经营进度、升级购买与章节解锁（中优先级）

- 现状：前四城主要走 `TryPurchase/CommitDay`，但内部仍有城市分支；扬州另写 `PurchaseYangzhou/CommitYangzhou`。各经营首页重复处理关卡开放、最佳成绩、金币不足、设备满级与购买反馈。
- 建议：共用购买事务、前置条件校验、逐级升级、保存回滚、成绩展示数据和章节解锁判断。城市提供设备目录、价格、解锁条件和奖励配置，页面保留自身美术与布局。
- 定位：`Scripts/Core/SaveService.cs`、`GuangzhouSave.cs`、`YangzhouSave.cs`；`Scripts/UI` 下各城市 `Hub`。

### 8. 订单生成基础设施与压力控制（中优先级）

- 现状：有公共确定性随机与订单模型，同时保留西安、广州、扬州生成器；顾客复杂订单压力控制分布在公共队列和扬州会话，广州另有到店前订单保护。
- 建议：共享固定种子重现、人数与订单配额校验、到店时间边界、延迟计时和容量限制。菜单组合、复杂订单上限、库存保护、教学指定单继续作为城市策略。
- 定位：`Scripts/Orders`、`Scripts/Customers/CustomerQueue.cs`、`Scripts/Guangzhou/GuangzhouOrderProtection.cs`、`Scripts/Yangzhou/YangzhouOrders.cs`。

### 9. 订单展示与操作反馈（中优先级）

- 现状：天津、武汉复用 `OrderBubbleView`、`CustomerPortraitView`；其他城市分别使用文字、卡片或按钮。成功、失败、库存不足、暂停等反馈也由各界面编写。
- 建议：共享订单剩余数量、完成标记、耐心显示与交付状态的数据来源；共享提示事件、减少动态效果支持和反馈清理。气泡外观、图标、人物与声音配置可不同。
- 定位：`Scripts/UI/OrderBubbleView.cs`、`CustomerPortraitView.cs`、`CoinCollectionFeedback.cs`；各城市 `DayScreen`。

### 10. 通用机制回归测试（贯穿以上工作）

- 现状：已有大量城市专项测试，金币专项目前覆盖天津和武汉；通用机制尚未以全部城市为测试参数覆盖。
- 建议：建立所有城市必须通过的测试集合：五人上限、第五位可交付、拒绝交付不扣货、重复操作不计款、暂停冻结、取消不丢货、存档失败重试、重开清理。部分交付城市验证正确交付恢复耐心；扬州验证放入托盘不恢复耐心。统一验证流失不计入满意度、小费四舍五入，并按城市额外验证独特制作玩法。
- 定位：`Scripts/Tests/CoinCollectionSelfTest.cs`、`WuhanSelfTest.cs`、`WuhanDeliverySelfTest.cs`、`StageFour*SelfTest.cs`、`XianSelfTest.cs`、`GuangzhouSelfTest.cs`、`YangzhouSelfTest.cs`。

## 用户已确认的评分和玩法规则（2026-09-09）

1. 满意度口径：流失顾客不计入，只按已完成订单的顾客计算平均值。已将天津15天配置、默认关卡配置和默认账本口径对齐，并增加配置校验。
2. 小费取整：统一四舍五入到整数，非负金额0.5向上；C# 使用 `MidpointRounding.AwayFromZero`。五城已共用 `Scripts/Orders/TipCalculator.cs`；先将配置小费率转换为十进制再计算，避免浮点误差改变半数边界。
3. 托盘与交付：扬州保留整盘上桌，不适用部分交付恢复耐心。商品放入备餐托盘不算交付，不触发耐心恢复。
4. 教学保护：允许存在，保留明确的教学配置或策略；本次确认并不意味着给所有城市新增无限时间或无限原料。

以上四项已落实到运行逻辑或保留符合规则的现有行为：教学保护保留，扬州入托盘和整盘上桌不恢复耐心，并增加相应测试。评分档位与质量扣分数值未被本次确认统一；城市独有的制作工序、火候、质量缺陷、设备升级收益、配方和订单结构仍保留。上文其余待统一项目仍是排查清单，不代表全部已完成。

## 建议实施顺序

先补齐已确认的顾客、金币、满意度和小费规则，遵循扬州整盘交付特例并保留教学保护；随后统一固定顾客位、交付提交、暂停取消和保存重试；再抽取库存、营业流程与升级进度。每一步都用跨城市回归验证。
