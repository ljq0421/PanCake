# 《煎饼开张》项目分析与优化台账

> 最后更新：2026-08-31  
> 当前阶段：P1 进行中（P0 工程项已完成，等待真人验收记录）  
> 原则：自动化通过只代表工程检查通过；手感、疲劳、学习成本与整体可玩性必须由真人试玩确认。

## 1. 总体结论

这是一个完成度较高的三章中式街头餐饮经营游戏。项目已经具备完整战役框架、三套差异化操作玩法、成长系统、存档、正式美术与较强的自动化测试基础。

当前成熟度可以概括为：早餐章接近主产品级完成度，面馆与夜市属于可玩的垂直切片；工程基础扎实，但在人工体验验证、三章品质统一、发布工程和长期维护成本方面仍未达到可放心对外发布的状态。

下一阶段不宜继续横向增加系统。更高价值的工作是把现有三章做齐、做稳，完成真人验证，并清理会持续拖慢迭代的架构与内容债务。

## 2. 游戏定位与核心循环

战役由三个依次解锁的店铺组成：早餐摊、面馆和夜市。三个店铺使用独立金币及成长进度，共享全局声望；营业日未结算时不能切换店铺。

核心循环为：

1. 按订单制作食物。
2. 根据实际操作与模型状态评分。
3. 服务顾客并收取付款。
4. 处理补货、浪费、耐心和营业时间。
5. 日结并购买成长。
6. 达成条件后解锁下一章节。

这套结构把“手艺操作”和“轻经营”连接起来：制作失误不仅影响分数，也会影响顾客耐心、收入、原料成本、浪费和跨日成长。

## 3. 三章玩法分析

### 3.1 早餐摊

早餐是当前真正的主干章节。四个经营区域围绕煎饼、油条、豆浆和包装饮品展开，其中煎饼承担最深的手艺操作。

煎饼并非简单动画或进度条，而是网格化模拟。覆盖率、厚度、湿度、熟度、损伤和酱料都会进入模型，评分读取模拟数据而不是画面像素。摊饼轨迹采用距离采样，操作结果较少受帧率影响。

经营侧包含最多五位顾客、耐心、库存、找零收款、浪费、开店备货、日目标与跨天升级。早餐成长内容明显多于后两章，是当前内容最完整、美术完成度最高，同时也是复杂度最高的章节。

主要风险：

- 五顾客订单卡与升级热点已改为渐进披露，但高峰期扫读效率与特殊规则的可发现性仍需真人验证。
- 早餐成长总量远高于面馆与夜市，可能形成前期过长、后期过短的战役曲线。
- 当前运行实现已是四区域，但大量资源及脚本仍沿用 `five_area` 历史名称。

### 3.2 面馆

面馆把操作重点从空间铺展改成速度与熟度控制。划动速度决定面条粗细，每次划动形成独立面批；不同粗细拥有不同最佳熟度窗口。未熟可以返煮但会受到评分上限约束，过熟则不可逆。

最终评分综合刀工、熟度、粗细匹配、份量、配方和时间。规则清晰，并且与煎饼形成了实质差异。

主要风险：

- 当前视觉较依赖深色功能面板、文字和分数反馈。
- 面条形态、锅内状态与熟度变化的食物表现弱于早餐。
- 连续制作时的疲劳、误划和学习成本尚未完成人工验收。

### 3.3 夜市

夜市要求玩家同时管理左侧烧烤与右侧油炸，并在中间装盘。烤物跟踪正反面热量；炸物模拟油温、炸制时间、起锅沥油和返炸。组合订单天然能够制造注意力分配与优先级决策。

主要风险：

- 默认界面已弱化精确温度、热量和时间，并保留显式详细数值开关；仍需真人确认定性反馈是否足以支撑稳定判断。
- 烟、颜色、气泡、声音等直觉反馈已经接入，但辨识度与长期疲劳度尚未通过足量真人试玩验证。
- 烧烤、油炸、翻面、起锅、调味和过火已接入独立夜市音效；仍需真人确认辨识度与疲劳度。
- 教学后的限时订单已按“烧烤单线 → 油炸单线 → 基础双拼”递进；后续多任务压力仍需足量真人组合单验证。
- 结算已按餐品指出本单最弱的一项操作，并给出下一单可执行动作；建议是否足够清晰仍需纳入 15 组组合单真人测试。
- 烤串翻面、烤串起串、炸物提篮和沥油装盘已增加暖金控件高亮、底部短提示与一次性提示音；仍需真人确认双线同时提示时的注意力分配是否自然。

## 4. 实现与工程分析

项目使用 Godot 4.7.1，逻辑分辨率为 1920×1080，以 PC 鼠标操作为主。代码规模约 3.2 万行 GDScript。

工程优势：

- 煎饼拥有独立模拟、渲染与评分层。
- 面馆、夜市各自具备明确状态模型和计分器。
- 存档已演进到 v12，包含延迟合并写入、临时文件、备份恢复和旧版迁移。
- 菜单支持线程化加载、新游戏确认和章节切换约束。
- 设置包含音量、全屏、UI 缩放、拖动灵敏度和按键重绑。
- 多处交互尊重系统的“减少动态效果”偏好。

工程风险：

- `game_session_store.gd` 超过 5000 行，混合了存档、战役、经济和章节状态职责。
- 早餐主工作台脚本体积较大，UI、经营流程和交互路由耦合较深。
- 大量 `Dictionary` 与字符串形式的 `session.call(...)` 把部分错误推迟到运行期。
- 面馆与夜市重复实现接单、付款、补货、日结、成长购买及快照恢复。
- 历史兼容逻辑和旧命名增加理解及修改风险。
- 文档与代码存在版本号、价格注释和升级数量漂移。
- 仓库资源体积较大，运行时素材、源素材、概念图和淘汰素材缺少清晰分层。
- Windows 导出、持续集成与可移植测试入口已经建立，但正式导出包仍需跨机器和人工发布验收。

## 6. 优势总结

1. 三章并非换皮：早餐强调空间轨迹，面馆强调速度和熟度，夜市强调并行协调。
2. 模拟数据真实参与评分，特别是煎饼操作能够实际改变覆盖、厚度和熟度。
3. 经营层与手艺层结合自然，失误会产生耐心、收入、成本和成长后果。
4. 自动化测试覆盖了单元、集成、存档迁移、GPU 交互和性能基准。
5. 早餐实体摊位式布局和中式街头餐饮美术具有明确辨识度。
6. 素材具备清单、哈希与生成流程约束，可追溯意识较强。
